# Agent Overload: Analysis and Fix

## The problem, concretely

OpenPoke spawns one long-lived execution agent per thread of work. The write-up
that accompanies the project names "Agent Roster Bloat" as an open gap:
*"Hundreds of agents compete for attention; scaling requires semantic search or
caching solutions."*

Reading the code, that phrase turns out to cover two separate mechanisms, which
compound each other.

**1. Reuse only ever happened on exact string equality.**

```python
# server/services/execution/roster.py (before)
def add_agent(self, agent_name: str) -> None:
    if agent_name not in self._agents:
        self._agents.append(agent_name)
```

The agent name is free-form text generated by the interaction LLM. Ask about the
same thread a week later and it might say `"Lunch w/ Keith"` where it previously
said `"Email to Keith about lunch"`. Those are different strings, so a brand-new
agent was created with an empty history — the prior thread's context became
unreachable. That isn't "the LLM forgot"; it's a naming-collision problem with no
canonicalisation layer underneath it.

**2. The entire roster was injected into every prompt.**

```python
# server/agents/interaction_agent/agent.py (before)
for agent_name in agents:
    rendered.append(f'<agent name="{name}" />')
```

Every agent, every turn, as a bare name with no description, recency, or
relevance filter. Prompt cost grew linearly and without bound as the roster did,
and the model had to pick reuse candidates by eyeballing a flat list of strings.

Fixing the first problem alone wouldn't have been enough — correctly-named
distinct agents still accumulate over time — so both are addressed here.

## What was built

### Two-stage routing

```
send_message_to_agent(name, instructions)
  │
  ├─ 1. exact name match? ─────────────► reuse immediately (no extra API call)
  │
  ├─ 2. embed + rank roster ───────────► top-k candidates
  │       (lexical overlap on failure)
  │
  ├─ 3. below similarity floor? ───────► create new (no extra LLM call)
  │
  └─ 4. LLM judgment over candidates ──► create new, optionally with a
                                          staged duplicate link
```

Stage 1 matters for cost, with one clarification worth being precise about: "no
extra API call" means no additional call beyond the interaction agent's own
turn, not that no model reasoning happens. The interaction agent is an LLM
invoked once per turn regardless of which branch fires — it reads the user's
message, decides what to do, and produces the tool call. When a request resolves
via exact match, including the disambiguation-resume case where the user says
"Chen" and the model has to recognise that means the `"Keith Chen lunch"` entry
still sitting in its context from the earlier `ambiguous_with` list and then
reproduce that name verbatim, that recognition is still real model inference. It
just happens inside the turn that was going to run anyway, rather than costing a
second, separate call the way stages 2 and 4 would. The common case is the model
reusing a name it just used, and that path costs about the same as it did before
this change — cheap in the sense of no added call, not in the sense of no
thinking involved.

Stage 2 uses embeddings via OpenRouter's `/embeddings` endpoint, the same API
key already configured, no new provider. If embeddings fail or time out,
retrieval falls back to lexical token overlap rather than failing the turn.

Stage 4 sees only the shortlist, never the whole roster, so its prompt stays
bounded regardless of roster size. An LLM-only matcher would likely have just
moved the bloat problem into a different prompt rather than removed it.

### Text similarity alone does not merge anything

One option — letting the LLM decide "reuse this agent" and routing the work
there directly — was considered and set aside. That turned out to be the
central design decision of this change.

An execution agent's entire history is loaded into every subsequent run. If the
matcher wrongly concludes that "lunch with Keith" continues the thread about
Keith's confidential contract review, those two contexts get permanently fused.
There's no rollback, no provenance marker, and nothing surfaces to the user. A
conservative prompt lowers that probability but can't bound it, and the failure
mode is silent, which is a particularly bad property for a failure to have.

There's an asymmetry worth naming: a missed link leaves a harmless duplicate
agent behind. A false merge corrupts an unrelated thread going forward. Those
aren't equally bad, so it seemed wrong to treat them as equally bad in the
design.

So linking is evidential and staged — and only one row of the table below is
actually proof. The rest reflects a judgment call about how to rank weaker
evidence, not a measurement:

| Evidence | Confidence assigned | Effect |
|---|---|---|
| Embedding similarity + LLM judgment | Weak (inference) | Stages a `possible_duplicate_of` link. Both agents stay separate and independently addressable. |
| Shared correspondent email address | 0.5 — chosen, not measured | Records the evidence. Same person isn't the same thread, so no merge. |
| Shared Gmail `message_id` / `draft_id` | 0.6 — chosen, not measured | Both agents touched the same email. Still no merge — see below. |
| Shared Gmail `thread_id` | 1.0 — definitional, not inferred | Clears the commit threshold, so an actual merge happens. |

Only the last row is conclusive, and it isn't really an inference at all: a
shared Gmail `thread_id` is the same conversation by construction. The 0.5 and
0.6 values are an ordering decision — message/draft evidence ranked above bare
correspondent evidence, both kept comfortably under the 0.9 commit threshold so
neither can trigger a merge on its own — rather than numbers pulled from a
calibration sweep the way the similarity floor described later was. If that
ordering ever needs revisiting, it would be against real merge outcomes, which
nothing here currently collects.

**Why message/draft evidence still shouldn't merge, even though it's real Gmail
data.** An earlier version pooled thread, message, and draft ids into one set
and scored any intersection 1.0. That turned out to be wrong: two agents can
legitimately touch the same email without being the same thread of work — two
different searches can surface one message, or one agent can forward what
another read. Combined with a staged text-similarity link, a single incidentally
shared message would have been enough to trigger an irreversible merge. The line
ended up drawn so a *thread* — the conversation itself — counts as proof, and a
*message* — an object both agents happened to see — does not.

This distinction was caught by an external adversarial review rather than by
the original tests, which only ever exercised shared thread ids and so never
challenged the equivalence. There are now negative tests for shared message and
draft ids.

The underlying idea is that the system doesn't have to guess forever. Once an
execution agent does real Gmail work, its log accumulates ground-truth
identifiers. Two agents referencing the same `thread_id` aren't just similar —
they're provably the same conversation. Confidence accrues as evidence arrives,
and only proof authorises the irreversible step.

Reconciliation runs after each execution, when new log entries may contain the
deciding evidence.

### Ambiguity: not guessing which one

Two people named Keith, both with a lunch thread. The user says "follow up on
lunch w/ Keith." Retrieval returns both at identical similarity — the gap
between them is 0.0000.

Asking the judge to choose here produces something close to a coin flip, and a
50/50 answer seemed worse than no answer at all — closer to a guess dressed up
as a decision. So when the top two candidates fall within
`agent_ambiguity_margin`, the system starts no work: no agent created, no link
staged, and the tied names are returned for the interaction agent to ask about.

An earlier version dispatched the work anyway and asked in parallel. That didn't
hold together: the execution agent could email the wrong Keith before the answer
arrived, and asking after an irreversible action doesn't accomplish much.
Holding the work is what makes the question mean anything.

**Resuming doesn't need extra machinery.** The natural objection is that holding
a request implies somewhere to park it, a resume path, and a timeout. It
doesn't, in this design: the user's reply is the resume mechanism. They say
"Chen," the model calls `send_message_to_agent` again with that exact name, and
it takes the exact-match fast path. The conversation loop already provides
whatever a pending-state machine would.

It also shifts the incentive a little. Previously the model was told "work
started, also please ask" — one of those signals reads as "handled." Now the
turn produces nothing unless the model speaks to the user, so the pressure to
ask is more structural than purely instructional. It's still not a hard gate — a
system-prompt section tells the model to clarify, and prompt instructions aren't
controls — but the design at least doesn't work against itself anymore.

Cost: one extra round-trip on genuinely ambiguous requests, roughly what a human
assistant would do, and only when two candidates land within 0.05 of each other.

### Merging is a pointer, not a deletion

`merge_agent()` sets `merged_into` on the absorbed record. Both roster records
and both log files stay on disk. What changes:

- `resolve_name()` follows the pointer, so anything still referencing the old
  name lands on the survivor. This matters most for triggers, which store their
  owner by name — a trigger created before a merge would otherwise reactivate an
  agent that no longer owns the thread.
- `ExecutionAgent.build_system_prompt_with_history()` concatenates merged-away
  transcripts ahead of its own, so the surviving agent actually inherits the
  context. Without this, the merge would be bookkeeping that recovers nothing.

### Retirement without a status field

An earlier draft had an `active → dormant → archived` enum recomputed by a
periodic job. That was cut. Relevance-ranked retrieval already bounds what the
model sees, so a discrete status field wasn't doing separate work, and it
introduced a subtle bug: treating trigger firings as "activity" meant a
recurring daily reminder looked perpetually engaged despite zero user contact.

What replaced it:

- A single `last_active` timestamp; "archived" is computed on the fly as
  `now - last_active > agent_archive_after_days`. Nothing persisted, nothing to
  recompute, no state to drift out of sync.
- Only live-chat delegation updates `last_active`. Trigger firings don't.
- Any agent owning a non-completed trigger is exempt from archival, however
  idle. A scheduled trigger is fairly direct evidence the user wants the work to
  continue, which is close to the opposite of an abandoned thread. This needed
  no new field — the triggers table already answers it.

Archival affects only the default prompt view. The embedding index still covers
every agent, and a `search_agents` tool gives the model on-demand access to the
full set. Nothing is unreachable; cold agents are just one lookup away instead
of occupying prompt space uninvited.

### Bounded prompts

`_render_active_agents` now renders name and description, and:

- Rosters at or below `agent_prompt_top_k` render in full, with no embedding
  call at all, so small installations pay no added latency.
- Larger rosters render at most `agent_prompt_top_k` agents total: the N most
  recently active fill their slots first (guaranteed inclusion, never dropped
  for semantic distance), and semantically-relevant candidates fill whatever
  budget remains. This is a capped fill, not a true union — if the N recent
  agents fall outside the semantic top-k, fewer than k semantic slots survive.
  The cap is deliberate: it's what keeps the prompt cost fixed regardless of
  roster size (see the N=200 comparison further down); a true union could grow
  past `agent_prompt_top_k` whenever the two sets don't overlap.

### Concurrency

Two races existed and both are closed now, each reusing a pattern already in
the codebase rather than adding new infrastructure:

- **Roster read-check-write** — two concurrent delegations could both miss each
  other and create duplicates. `create_or_link` now holds an `asyncio.Lock`.
- **Same-agent concurrent execution** — `ExecutionBatchManager._batch_lock` only
  ever guarded batch counters, not the `runtime.execute()` call, so two turns
  hitting one agent could load the same transcript and append interleaved
  results. This is now serialized by a per-agent lock mirroring
  `ExecutionAgentLogStore._lock_for`. Unrelated agents still run in parallel.
  Better dedup makes this collision more frequent, so it needed fixing
  alongside the rest.

### Embedding model versioning

Each stored vector records the model that produced it. On a model change, stale
vectors are ignored for cosine scoring and that record falls back to lexical
matching. This isn't optional bookkeeping: two models can emit vectors of the
same dimension, so without the tag, a model swap would yield similarity scores
that look numerically plausible while meaning nothing — wrong, but invisible.

The intended strategy, if the embedding model is ever swapped, is to re-embed
stale records lazily — refresh a record's vector the next time it's touched,
rather than run a bulk migration. `AgentRoster.update_embedding` exists for
this, but it isn't wired into the live routing path — `interaction_agent/tools.py`
only ever writes an embedding at agent creation, never on a stale-model read.
Today `update_embedding` is called only from test fixtures. So as it stands, a
record stuck on an old model stays on lexical matching indefinitely, with no
automatic path back to embedding-based scoring.

## Testing

### Deterministic unit tests — `python -m pytest server/tests -v`

111 tests, no API key, no network, well under a second. Coverage:

- **Similarity primitives** — known-value cases (orthogonal, identical, 45°),
  plus degenerate inputs (empty, dimension mismatch, zero vector).
- **Retrieval** — ranking order, top-k, lexical fallback, and that a
  stale-model vector is refused for cosine scoring.
- **Roster** — legacy string-list format still loads, malformed JSON degrades to
  empty, full record round-trip through disk.
- **Slug collisions** — `"Keith/Lunch"` and `"Keith Lunch"` slugify identically;
  the tests check they get distinct records and distinct log files.
- **Retirement** — threshold boundaries, and that a live trigger exempts an
  agent idle for a year.
- **Merging** — redirection, non-destructiveness, and a pointer-cycle guard.
- **Concurrency** — per-agent locks actually serialize (no interleaving), and
  five concurrent creates of the same name yield one record.
- **Routing branches** — every path in `send_message_to_agent`: exact-match fast
  path (asserts zero embedding calls), empty roster, below-floor short-circuit
  (asserts no LLM call), staged linking, embedding-failure fallback, and
  rejection of a hallucinated agent name.

Two safety properties are asserted directly, since they're close to the whole
point of the design: `test_similar_task_stages_a_link_but_does_not_merge` (text
similarity leaves both agents separate) and `test_weak_evidence_alone_never_merges`
(a shared correspondent raises confidence but doesn't commit).

### Evaluator — `python server/tests/eval_agent_matching.py`

Needs a real `OPENROUTER_API_KEY` and costs real tokens, so it's a manual run
rather than part of the default suite.

It's split by determinism, which is what keeps calibration cheap:

- *Phase 1 — retrieval.* Embeddings are deterministic for a fixed model, so
  every text is embedded once, cached, and the similarity threshold is then
  swept across many values entirely offline — zero extra API calls, zero
  run-to-run noise. The shipped floor was picked off that curve rather than by
  feel. This phase also reports recall@k — an agent absent from the shortlist
  can never be linked, whatever the LLM decides, so retrieval failure and
  judgment failure are diagnosed separately.
- *Phase 2 — judgment.* The LLM can answer differently on identical input, so
  each case runs N times (default 5) and the report shows a per-case flip rate.
  A single pass would hide exactly the instability worth knowing about.

**Dataset** (17 cases): true reuse via paraphrase, abbreviation, typo, and
indirect reference; adversarial near-misses (same person different topic, same
domain different company) which represent the specific false-merge risks;
genuinely new work; and an empty-roster first-agent case.

**Metrics**: a full confusion matrix, with the false-merge rate reported
separately from accuracy. Correctly creating a new agent is a true negative, not
a true positive — collapsing the two would inflate recall, which the harness
tries to avoid.

**Acceptance thresholds** are explicit pass/fail rather than "looks reasonable":
zero false merges on the adversarial set, and recall strictly better than the
exact-match baseline, which is run over the same cases so the improvement is
measured rather than assumed.

**Statistical caveat**, printed by the harness itself: at this sample size, zero
observed false merges bounds the true rate at roughly ≤25% with 95% confidence
(rule of three). That's enough to catch a badly calibrated threshold; it isn't
enough to certify rarity in production, and reporting "0%" without that
qualifier would overstate what was actually shown.

## Live results

Run against OpenRouter with `openai/text-embedding-3-small` and
`anthropic/claude-sonnet-4`, the models the system actually ships with.

### The assumption the design rests on

Retrieval only works if a genuine paraphrase scores above a same-person,
different-topic request. That was measured rather than assumed:

| | text-embedding-3-small | nvidia/nemotron-3-embed-1b:free |
|---|---|---|
| Worst true reuse (a typo'd request) | 0.6440 | 0.4226 |
| Best adversarial (same person/topic) | 0.5691 | 0.6131 |
| Separation | +0.075 | −0.19 |
| Threshold exists? | Yes | No |

The shipped model separates the classes. The free model inverts them — it
scores "order a birthday gift for Keith" higher than a genuine typo'd follow-up
about lunch with Keith. No threshold fixes that; on the free model this design
would both miss real reuse and confidently match the wrong thread. Cost
efficiency was one of the gaps named in the original write-up, so this seemed
worth testing rather than assuming, and the answer is that this particular
saving isn't available.

### The threshold: calibrated, then found to be overfit, then rebuilt

This is probably the part of the evaluation most worth walking through, because
the first answer here turned out to be confidently wrong.

**First pass.** A sweep over one labeled set suggested 0.60 was optimal — it
kept 5/5 true reuse and let zero adversarial cases through to the judge. Clean
separation, picked from data rather than feel. That value shipped.

**Then the ablations, run live, disagreed.** On a different set of scenarios,
the same 0.60 floor dropped recall to 33%, while removing the floor entirely
gave 100%, with zero false merges either way. A threshold that looked optimal on
one dataset turned out to be actively harmful on another.

**The likely cause.** Pooling every similarity measured across both sets against
`text-embedding-3-small`:

```
TRUE REUSE   0.246 ────────────────────────────── 0.765
ADVERSARIAL          0.505 ─────────── 0.665
UNRELATED    0.172
```

The classes interleave almost completely — they overlap by 0.419. The original
set happened to contain reuse cases scoring 0.64–0.77 and adversarials scoring
0.50–0.57, which made a separating threshold look available. That looks like an
artifact of case selection — overfitting to the calibration set, and the only
reason it surfaced is that a second dataset disagreed.

**What follows from that.** A similarity floor doesn't look like it can be a
safety mechanism here; no value cleanly separates the classes. It can only
filter genuine noise, which measures around 0.17. Real discrimination has to
come from the judge, and the live evaluation suggests it does that reasonably
reliably, abstaining correctly on every adversarial case tested.

So the floor dropped from 0.60 to 0.20 — low enough to be close to inert, high
enough to skip obviously unrelated requests. The effects, as measured:

| | floor 0.60 | floor 0.20 |
|---|---|---|
| Ablation-set recall (live) | 33% | 100% |
| Routing-set recall (live) | 100% | 100% |
| False merges (live, both sets) | 0 | 0 |
| Cases reaching the judge | 9/17 | 14/17 |

This looks better on quality, at some cost — more requests now reach the LLM —
and that trade was made deliberately: the floor was buying cost savings, not
safety, and paying for them in recall.

**A limitation no threshold fixes.** The weakest true-reuse case scores 0.246:
"Ask them to raise the equity portion." A pronoun carries no signal about which
thread it belongs to, so embedding-based retrieval can't really match it. The
no-retrieval ablation scored 100% on exactly this case — the LLM can resolve
"them" when shown the full roster. Retrieval fails precisely where the model
succeeds. Resolving anaphora against conversation history before embedding would
likely fix it, and it isn't implemented here.

### Routing quality (17 cases × 5 runs = 85 decisions)

Driven through `send_message_to_agent`, the shipped path, rather than the judge
in isolation, so the exact-match fast path, similarity floor, and ambiguity
check are all exercised as they would be in production.

- Accuracy 100%, precision 100%, recall 100%, F1 1.00
- Committed false merges: 0 across every live run
- Exact-match baseline recall: 0% on the same cases
- Judge consulted on 14 of 17 cases (the harness reports this — see below)

**Staged links and committed merges are scored separately, and that split is
close to the whole point of the design.** The judge stages a link; the evidence
gate decides whether it ever becomes a merge. Conflating them either credits the
gate for the judge's caution or blames the judge for a failure that never
reached the user. Measured live:

| | observed |
|---|---|
| Links staged by the judge | 60 |
| Merges committed after the gate | 0 |

(The run count behind that 60 isn't reconstructable after the fact — see the
~340-decision figure below for the closest verifiable scale. A fresh,
fully-reproducible single run of the same 85-decision harness, done later,
staged 30 links, committed 0 merges, still consulted the judge on 14/17 cases,
and reproduced accuracy/precision/recall/F1 at 100%/100%/100%/1.00 with a 0%
flip rate — every case answered identically on every one of its 5 runs.
Different absolute count, same shape of result.)

**The judge does make mistakes, and in one run the gate caught them.** Across
roughly 340 live judgment decisions over the course of this work, one batch of
85 produced 3 bad links — the model linked "Vercel contractor invoice" to the
Vercel *offer* thread, and a dental billing question to the dental appointment
thread. The other ~255 decisions produced none. So the error rate looks low
(around 1%, with wide uncertainty) but not zero, and a single 5-run sample can
plausibly show either 0 or 3 — confirmed directly: the fresh 85-decision run
cited above produced zero bad links that time, the same kind of instability seen
in the A5 evidence-gate ablation rerun (see EVALUATION.md, Step 4).

Each of those three was stopped by the evidence gate, because neither pair
shares a Gmail thread id. That's the central design decision holding up against
real model output.

This also revises an earlier reading in this document's history. A 3-run sample
had shown no bad links at all, from which the working conclusion at the time was
that the gate was unproven. In hindsight that looks underpowered rather than
proof of absence — a reminder that "zero observed" and "the rate is zero" are
different claims, and small samples can't distinguish them.

**The dataset needed rebuilding twice before the numbers meant much.** The first
live run scored 100% while every adversarial case fell below the similarity
floor, so the judgment stage was never consulted on anything hard, and the score
mostly measured the threshold with the LLM idle behind it. The harness now
prints how many cases reached the judge for exactly that reason.

Two rounds of cases were added to address it:

1. **Two people named Keith, both with a lunch thread.** Retrieval scores them
   0.0089 apart, effectively indistinguishable. In the shipped pipeline this
   trips the ambiguity check, so the system asks the user rather than guessing;
   the paired case ("Keith Chen") links correctly 5/5, which suggests it's
   discriminating on the distinguishing detail rather than freezing whenever two
   names collide.
2. **Three cases that reach the judge alone and need to be refused** — selected
   by measuring real similarity first: dinner-with-Keith (0.67) against the
   lunch thread, a Vercel invoice (0.60) against the Vercel offer, a dental
   billing question (0.66) against the dental appointment. Each arrives as a
   single strong candidate, so the judge has to actively decline. These are the
   two cases where it sometimes doesn't — see the staged-link finding above.

Without those additions, the judge's abstention — arguably the safety-critical
half of its job — was effectively unmeasured while the report still read 100%.

Statistical honesty: 40 adversarial decisions bounds the true false-merge rate
at roughly ≤8% at 95% confidence (rule of three). Enough to catch a badly
calibrated threshold; not enough to certify rarity in production.

### A result that didn't match the hypothesis

The degradation experiment predicted that a large unranked roster would dilute
the model's attention and hurt selection. Measured live with 18 labeled cases
per point, and — as of a later fix — with real embeddings driving retrieval on
both sides rather than a synthetic stand-in: `eval_degradation.py --live`
previously only made the judge call real while shortlisting with a hand-built
embedding model, which didn't match what "real embeddings live" was meant to
mean elsewhere in this document. That's fixed, and the run below reflects it:

| N | old (full roster) | new (top-15) |
|---|---|---|
| 11 | 100% [82–100] | 100% [82–100] |
| 15 | 100% [82–100] | 100% [82–100] |
| 25 | 100% [82–100] | 100% [82–100] |
| 50 | 100% [82–100] | 100% [82–100] |
| 100 | 100% [82–100] | 94% [74–99] |
| 200 | 94% [74–99] | 100% [82–100] |

Brackets are 95% Wilson intervals. Every interval overlaps every other one. At
this sample size there's no resolvable difference between showing the model 200
unranked agents and showing it a ranked 15, and no resolvable degradation with N
in either arm. Sonnet handled 200 candidates about as well as 11 in this test.

An earlier run at 6 cases showed 83% at N=200 and looked like a real effect. It
turned out to be a single miss. Tripling the sample moved it to 94%, also a
single miss. That's part of why the intervals are printed — a bare "83%" reads
as a finding, while "83% [36–99%]" reads closer to what it actually was.

The claim narrows as a result: prompt pruning looks justified by cost, not
accuracy. At N=200 the old rendering costs 3.9× the tokens, on every turn,
indefinitely. That argument holds on its own. The accuracy argument doesn't, and
is withdrawn — the dilution effect, if it exists, is smaller than this
experiment can detect.

This lines up with the offline finding that degradation tracks confusable
density rather than raw count. Two hundred agents about strangers don't seem to
interfere with each other much. Five agents about the same person do.

Worth stating plainly: the cost crossover moved as the dataset grew. With
descriptions attached, the new rendering is more expensive below roughly N≈100
and only pays for itself above that. Whether that's a good trade depends on the
roster size expected in practice — for a small personal install it's a net cost,
justified by the matching quality descriptions enable rather than by tokens
saved.

## Design decisions worth explaining

**Why not a stable opaque ID as the primary key?** It's the textbook answer, and
an external adversarial review recommended it. It was declined deliberately: the
actual bug is lossy slug collisions, which is closed by disambiguating at one
choke point in the roster. An ID rewrite would touch the log store, the triggers
table, the runtime constructor, and the interaction agent's own tool vocabulary
(it has no concept of an ID — it refers to agents by name). That's a fairly
large blast radius for the same bug fixed a narrower way.

**Why not `numpy` or a vector DB?** Roster sizes here are expected to be in the
hundreds, maybe thousands. Brute-force cosine over short vectors runs in
microseconds. At genuinely large scale an ANN index (FAISS/HNSW) would make more
sense, but adopting one now would be speculative.

**Why is retrieval skipped for small rosters?** Because the fix shouldn't
regress the thing it's trying to improve. Adding a network round-trip to every
turn for an installation with four agents would make the product worse, not
better.

**Why no reranker between retrieval and the judge?** Considered, and set aside
based on the evidence available rather than intuition: `recall@k` is already
100% in the live eval, so there's little for a reranker to recover; the
no-retrieval ablation (showing the judge the full roster) also scored 100%, so
the shortlist step doesn't look like where quality is lost; and the LLM judge
already reads the request and every candidate jointly to decide, which is close
to the same job a cross-encoder reranker would do — adding one would mean a
second model doing the first one's work. The trigger to revisit this would be
`recall@k` degrading as the roster grows, which `eval_degradation.py` measures
directly and which is currently flat.

## Known limitations

- **Duplicates can still exist in the moment.** Evidential linking means
  near-duplicate agents get created and merged later once proof arrives. For
  work that never touches Gmail (a pure reminder, say), no structural evidence
  ever materialises and the link stays pending indefinitely. This still looks
  better than exact-match — the system knows they're related, and
  prompt-pruning keeps the duplicate out of context — but aggressive dedup and
  never-false-merge genuinely trade off against each other, and this design
  leans toward safety.
- **Prompt-rendering selection quality — now tested against real embeddings,
  and the recency guarantee's ablation is inconclusive rather than untested.**
  `_render_active_agents` previously had no live coverage at all: every unit
  test stubs a uniform vector for the query, and none of the test-fixture agents
  are ever given a stored embedding, so those tests exercise the lexical
  fallback rather than cosine ranking. A live check now exists
  (`eval_degradation.py --live`, section (d)): at N=51 with real embeddings on
  both sides, recall@15 was 100% (18/18) — the true match wasn't dropped in this
  run. The same run also gave the recency guarantee its first actual ablation,
  previously just noted as never having been measured: a vague, pronoun-style
  follow-up for a just-touched agent survived both with and without the recency
  guarantee. That doesn't prove the guarantee unnecessary — one query against
  one roster is the same underpowered-sample situation flagged elsewhere in this
  document — but it doesn't show it load-bearing either. The reasoning for
  keeping it (anaphora, frozen descriptions, margin erosion under confusable
  density — see "Design decisions worth explaining") still holds independent of
  this one result; what's missing is a case that actually forces the guarantee
  to matter.
- **A duplicate created because the true match never rendered can still merge
  later, though it isn't guaranteed to.** If retrieval quality is ever the
  reason a duplicate got created — the model never saw the true match in its
  prompt and invented a new name — that new `send_message_to_agent` call still
  runs its own independent embed+rank over the full roster (`tools.py:169`, not
  capped at `agent_prompt_top_k`), so it gets a second chance to stage a link
  the prompt view missed. But that second chance shares the same embedding
  model as the first, so a systematic ranking weakness could miss both; and even
  a successfully staged link only becomes a merge once real Gmail evidence
  arrives, which folds this failure mode into the "duplicates can still exist in
  the moment" limitation above — reached by a different route (invisibility
  rather than weak text similarity), with the same unresolved-until-evidence
  outcome.
- **Descriptions are frozen at creation.** A thread that evolves over months
  keeps its original semantic anchor, which can degrade match quality in either
  direction over time. Periodic re-summarisation would likely help and isn't
  implemented.
- **Evidence extraction depends on log truncation.** The execution runtime
  truncates logged tool arguments to 200 characters and responses to 500. A
  `thread_id` in a long payload can get cut off, so structural evidence is
  best-effort rather than guaranteed.
- **The eval doesn't cover the merge path end-to-end.** It measures the linking
  decision. Merge promotion via shared `thread_id` is covered by unit tests with
  mocked logs, not by the live evaluator, which would need real Gmail data
  across two agents.

## Separately: a pre-existing issue found while reading the code

Not fixed here, since it's out of scope for agent overload and probably
deserves its own change, but worth flagging.

`interaction_agent/tools.py` holds one module-level `ExecutionBatchManager`
shared across the entire application, and the interaction agent is only
notified when a batch fully drains (`pending == 0`). So a fast agent's result
can be withheld until the slowest agent in the batch finishes — up to the 90s
timeout — with no partial update to the user in the meantime. Because the
manager is global rather than scoped to a turn, an agent dispatched by a later,
unrelated message can also join a still-open batch and end up held back by an
earlier straggler.

The trigger scheduler avoids this by constructing a fresh `ExecutionBatchManager`
per firing (`trigger_scheduler.py:92`), which is likely why scheduled reminders
surface independently. The live-chat path would probably benefit from doing the
same, scoped per interaction turn.
